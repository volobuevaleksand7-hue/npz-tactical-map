# Второй планировщик на VPS — невидимый обычным инструментам

## Факт

Живое расписание флота на `hermes-vps` держится в **трёх** местах, которые не синхронизированы и не видят друг друга:
1. системный `crontab -l`;
2. **`/root/.hermes/cron/jobs.json`** (собственный планировщик Гермеса, ~29 заданий) — не отображается ни в `crontab -l`, ни в `syslog`, ни в `cron.log`;
3. systemd timers.

Единственный достоверный список — снимок `agents/fleet-snapshot.sh` (пишет `docs/agents/FLEET-SNAPSHOT.md`, `--check` возвращает RC=1 при расхождении).

## Что сломается, если не знать

- Диагностируя дубль публикации/задания, посмотришь только `crontab -l` и решишь, что второго источника нет — а он есть, и продолжит дублировать/конфликтовать.
- Отключив задание в `crontab -l`, решишь, что оно остановлено — если та же логика жила в `jobs.json`, она продолжит работать.
- Искать разницу между «двумя планировщиками» по ИМЕНИ задания бессмысленно — сравнивать нужно **промпты/логику**, а не названия. Реальный прецедент: смок-тест падал на каждом пуше из-за рутины NEWSWATCH с древним промптом, читавшей собственный Telegram-канал проекта (24 эха @NPZmap в архиве, 10 с координатами Москвы) — задание называлось иначе, чем актуальное, и не бросалось в глаза при сверке по имени.

## Как проверить факт

```bash
ssh hermes-vps 'cd /root/npz-tactical-map && bash agents/fleet-snapshot.sh --check'
cat /root/.hermes/cron/jobs.json   # на hermes-vps — второй источник, руками не правится
```

`jobs.json` руками не правят — только через штатный интерфейс Гермеса; при экстренной правке (как 02.08.2026, когда чистили `$(date ...)`-подстановку из 7 заданий) обязателен бэкап `.bak-<timestamp>` рядом.
