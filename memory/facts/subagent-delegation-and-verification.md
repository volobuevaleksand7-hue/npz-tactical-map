# Делегирование ресёрча/данных субагентам — два известных отказа

## Отказ 1 — субагент раздаёт работу дальше и выходит пустым

31.07.2026: агент, которому поручили добыть площади складов, **дважды** раздал задачу под-субагентам и вышел, не записав ничего (0 площадей, файл не тронут). Потребовалось явное «делай сам, без делегирования» + сокращение объёма задачи (топ-14 → топ-12), только с третьего захода агент сдал результат. Урок: для задач ручного ресёрча/сбора данных цепочечное делегирование («субагент поручает субагенту») склонно схлопываться в пустой результат без ошибки — прогресс нужно проверять по факту записанных данных, не по отчёту «сделано».

## Отказ 2 — MiMo выдумывает числа или подхватывает чужую сессию

24.07.2026, черновик статьи про удар по складу в Петербурге: MiMo дважды падал (repetition-guard срабатывал, плюс один раз подхватил ЧУЖУЮ сессию с выдуманными цифрами). Пойманные глитчи при финальной вычитке: китайские иероглифы внутри русского слова, выдуманное «десять объектов в семи регионах» (было удалено), лишний пересчёт «6→7 субъектов». Ни одна из этих ошибок не была очевидна без построчной сверки с первоисточниками.

## Правило

- Черновик от внешней модели (MiMo и аналоги) — вычитывать построчно против первоисточников перед публикацией, особенно числа и счётчики объектов/регионов. Не полагаться на "выглядит связно".
- Для задач сбора конкретных данных (площади, координаты, суммы) — не давать субагенту делегировать дальше без проверки; если задача не выполнена за один-два захода, сокращать объём, а не углублять цепочку.
- См. также `memory/facts/json-array-bloat-and-migration-verification.md` — тот же принцип «round-trip своим декодером» применительно к миграциям данных, не к ресёрчу.
