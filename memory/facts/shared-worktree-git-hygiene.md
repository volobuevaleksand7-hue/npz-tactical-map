# Общее рабочее дерево — что его ломает

## Что сломается, если не знать

Своя или чужая незакоммиченная UI-правка (`app.js`/`index.html`/`analytics.html` и т.п.) исчезнет без явной ошибки — просто засташится или снесётся, и придётся восстанавливать из `git stash list`/reflog, если повезёт их найти вовремя.

## Рецидивы разрушительного git в общем дереве (репозиторий фиксирует минимум 4)

1. **`git pull --rebase --autostash` — клоббер, минимум 3 раза за разные сессии.** Автостэш засасывает ЧУЖОЙ незакоммиченный `app.js`/`index.html` без предупреждения. Официальный `agents/git-sync.sh` безопасен (коммитит `data/` первым, без `--autostash`) — проблема всегда в РУЧНЫХ git-командах отдельных сессий или скриптов публикации (`docs/seo-playbook.md` даже рекомендовал `git pull --rebase --autostash` как «нормальную» гигиену — это устаревшая рекомендация, противоречащая практике).
2. **`git reset --hard origin/main`.** 08.07.2026: сторонний локальный агент дёрнул `reset --hard` в рабочем дереве, пока правки `radar.html`/прокси были готовы, но не закоммичены — снёс их вместе с `version.json`/`CHANGELOG.md`. Восстановлено переналожением из истории.
3. Собственный тестовый откат может задеть чужую работу тем же способом — дважды за одну сессию (30.07.2026) `git reset --hard` в общем дереве съедал незакоммиченную правку самого автора.

## Правило

- **Никогда** `git pull --rebase --autostash`, `git add -A`, `git reset --hard` в общем дереве. Данные — только `agents/git-sync.sh "<msg>"` (трогает лишь `data/`). Свои файлы — `git add <явный список>` + коммит СРАЗУ после правки.
- Долгая/многофайловая UI-работа при активных других агентах → отдельный `git worktree add ../npz-<slug> -b <slug>`, работать там, push, слить и удалить worktree.
- Правки хуков/фронта коммитить сразу; тесты и экспериментальные откаты гонять только в worktree, не в общем дереве.

## Смежная ловушка: не путать «отставший worktree» с «потерянными данными»

02.08.2026: заброшенный `.claude/worktrees/zen-albattani-*` (3 коммита от 22.07) показал пугающий diff «586 файлов, −64k строк» против `origin/main`. Это было НЕ удаление — worktree отстал на 11 дней от ушедшего вперёд origin, а содержимое давно доехало до прода другим путём. Перед тем как паниковать по большому диффу, проверить ahead/behind (`git log --oneline <worktree>..origin/main` и обратно), а не читать diff как «что было удалено». После проверки — `git worktree prune`, брошенные worktree регулярно копятся и путают диагностику.
