# Раздутый однородный JSON и обязательная проверка миграции

## Наблюдение о размере

`data/azs-stations.json` (9609 записей) весил 1,66 МБ. Корень раздутия — не значения, а **повторение длинных имён ключей на каждую строку** (× 9609). Поштучные твики (сокращение отдельных полей, обрезка precision) давали только 1,34× сжатия. Перевод схемы в **табличную/колоночную форму** (общий список имён полей один раз + строки-значения) дал 1,66 МБ → 505 КБ, **3,35×**. Правило: для больших однородных массивов JSON первым делом проверять экономику именно схемы (ключ-на-строку vs таблица), а не резать поля по одному.

## Обязательная проверка после миграции: round-trip тем же декодером

Правило: **миграцию данных субагента проверять round-trip'ом ЕГО ЖЕ декодером**, не полагаться на «прогнал — сошлось». Формулировка «проверил, всё сходится» — не доказательство корректности сама по себе.

Конкретный случай, пойманный именно так: миграция `azs-stations.json` в табличную схему дала регрессию дедупликации — **247 станций Teboil были подписаны «Лукойл»**. Причина: у объединяемых записей поле `brand` не совпадало с реальной вывеской конкретной станции, а дедупликатор брал МАЖОРИТАРНЫЙ label по группе вместо индивидуального. Поймано прогоном декодера через `node` против `git show HEAD:` — то есть тем же кодом, которым фронт реально читает файл, а не визуальной проверкой диффа.

Фикс — не заплатка на 247 записей, а общее правило: индивидуальная подпись станции пишется ВСЕГДА при расхождении со словарным брендом, мажоритарный label не используется для перезаписи индивидуального значения.

## Что я сломаю, если не буду это знать

- Оптимизирую большой JSON точечными твиками полей вместо смены схемы — потрачу время на 1,3× там, где смена схемы даёт 3×+.
- Приму миграцию по «дифф выглядит разумно» без прогона реального декодера потребителя — рискую пропустить систематическую ошибку дедупликации/маппинга, которая не видна в сыром JSON, но видна только после декодирования тем же кодом, что на фронте.
