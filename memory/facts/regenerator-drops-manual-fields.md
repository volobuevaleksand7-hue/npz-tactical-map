# Регенератор стирает то, что не знает как перенести

## Механизм

Скрипт X пересобирает `data/Y.json` целиком из своего источника (внешнего API, `strikes.json` и т.п.). Поле `Z` в этом файле заполнено вручную ДРУГИМ прогоном (ресёрчем, другим агентом) и не входит в источник скрипта X. Любой прогон X «в рамках чужой задачи» (не связанной с полем `Z`) стирает `Z` молча — JSON остаётся валиден, ошибки нет, только данные пропадают.

## Что сломается, если не знать

Витрина будет молча показывать пустые/дефолтные значения там, где раньше была добытая вручную цифра — и это не всплывёт как ошибка, потому что схема не нарушена.

## Рецидивы

1. **`data/warehouses.json`, поле `area_m2`.** 31.07.2026 добыли `area_m2` + `area_source_url` для 14 складов WB (ручной ресёрч под инфографику). Через сутки, 01.08, инфографика молча показывала «0 площадей из 56 объектов» — `fetch-warehouses.py` (пересобирает объекты из `strikes.json`) прогнали в рамках ЧУЖОЙ задачи («кнопка канала на страницах»), и он не переносит ручные поля при пересборке. Бисекция по истории файла нашла точный коммит, где 14 → 0.
2. **Тот же класс, что `npz-data-wipe-cross-routine`** (по auto-memory: `git add data/` соседней рутины обнулял `fuel-voices` 96→0) и `npz-fuel-availability-region-wipe` (агент срезал покрытие АЗС с 88 регионов до 13, прогнав НЕ тот скрипт в рамках другой задачи).

## Правило

Фикс не в том, чтобы «больше не запускать генератор» — он должен запускаться. Фикс — **мерж по `id` перед перезаписью**: регенератор обязан читать текущий файл, переносить в него ручные/внешние поля по стабильному ключу, и только потом писать результат. Порядок работ важен: сначала фикс мержа, потом восстановление утраченных данных из старого коммита — иначе следующий прогон снова всё сотрёт. Доказательство фикса — не «код выглядит правильно», а реальный прогон скрипта с проверкой «было N, стало N» на уже заполненном поле.

Регресс-тест на этот сценарий стоит добавлять в `demo()`/`--selfcheck` скрипта, который переносит поля.
